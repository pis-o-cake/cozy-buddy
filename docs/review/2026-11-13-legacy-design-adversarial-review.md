# 이전 설계(v3.4) 적대적 검토

이전 설계서 v3.4는 재설계의 사양으로 계승하지 않는다. 이 설계는 실측하지 않은 리서치 수치 위에 서버
인프라와 추상화를 먼저 쌓았고, 가장 큰 미지수인 태블릿 오디오는 일정의 맨 뒤에 두었다. 제품 정체성
("로컬 LLM이 두뇌")은 v3.3의 클라우드 우선 전환으로 스스로 무너졌는데, 그 정체성에 기대던 GPU 서버·
PostgreSQL·프라이버시 주장은 그대로 남았다. 여기에 2026년 하반기에 기본 TTS 엔진의 개발이 종료되고
Home Assistant가 태블릿 음성 위성과 MCP 서버를 정식 지원하게 되면서, 기기 제어와 TTS 결정의 전제도
바뀌었다. 재설계는 아래 스파이크로 실측한 뒤 ADR로 결정한다.

## 검토 요약

검토 대상은 이전 시도의 원문, 곧 cozy-buddy-server 레포의 `docs/`(revision `6f8fbe6`)다. 설계서
v3.4(`cozy-buddy-design-v3.md`), 기능 명세, v2 설계서, 리서치 8편이 여기에 들어 있다. 파일은
`https://github.com/pis-o-cake/cozy-buddy-server/blob/6f8fbe6fbdc7d00c33e03d11dc9cec4eafe6d6ac/docs/<파일명>`에서 열며(v2 설계서는 `docs/archive/`, 리서치는 `docs/research/`), 아래 줄 번호는 이 revision 기준이다.
검토는 두 갈래로 진행했다. 하나는 원문을 독립적으로 반박하는 설계 검토이고, 다른 하나는 2026-11-13
기준 외부 기술 현황 조사다. 아래 위치 표기에서 `v3`는 설계서 v3, `FS`는 기능 명세, `R-*`는
`research/` 문서이며, `L`은 줄 번호다.

결론은 세 가지로 모인다.

- 무엇을 만들지가 흔들린다. 정체성, 우선순위, 범위가 문서 안에서 서로 다르다. 범위가 1인 개발
  용량을 넘는다는 점은 이전 시도가 이미 보여 주었다. 9개월 동안 남은 것은 텍스트 챗봇 수준의 1차
  서버(`legacy` 브랜치), 시계·설정 화면만 있는 허브 앱, 설계서 3판, 그리고 v3를 따라 다시 쓴 서버의
  Phase 0~2 구현(`main`, 2026-07)이다. 실제 태블릿에서 음성이 한 번이라도 오간 적은 없다.
- 직접 만들 필요가 없는 것을 직접 만들려 했다. 기기 어댑터, 방 모델, 상태 구독, 스케줄 자동화,
  Matter 컨트롤러 운영이 그렇다. 2026-11 기준으로는 Home Assistant가 이 전부와 LLM용 MCP
  인터페이스까지 제공한다.
- 위험 순서가 거꾸로다. 원거리 웨이크워드, 상시 마이크, 자기 TTS에 반응하는 self-wake, 알람
  신뢰성이 가장 크게 미검증인데, 이들이 5.5주의 서버 작업 뒤에 배치됐다.

검토를 통과해 유지하는 부분은 다음과 같다.

- 앰비언트 허브 UI 방향: 시계 화면, 그 위에 얹는 대화 오버레이, 야간 디밍과 번인 대책
  (v3 §10-5, [hub-ambient.html](https://github.com/pis-o-cake/cozy-buddy-server/blob/6f8fbe6fbdc7d00c33e03d11dc9cec4eafe6d6ac/docs/design/hub-ambient.html)).
- 오디오 버퍼 패턴: 온디바이스 웨이크, pre-roll 링버퍼, 단일 AudioRecord 팬아웃(v3 L417·L887-888).
  패턴만 유지하고 엔진은 정하지 않는다.
- 가설 하나: 지연의 지배 요인은 VAD 종료 판정이다(v3 L419). 사실이 아니라 1순위 측정 대상으로 둔다.
- 제품 동작 규칙: 확인 질문은 3가지 경우로 제한한다(v3 L699). 방 인지 해석 규칙 1~4(v3 §8-3).
- LLM 사용 결함 체크리스트(v3 L1046): `role:"tool"` 표준 주입, 최종 응답 이중 생성 금지, 기기 목록
  주입, reasoning 채널 분리.
- 태블릿 선정 체크리스트(R-android-audio L207)와 상시 화면 리스크 인식(v3 L926).
- 운영 위생: 원본 오디오 기본 미저장, 영어 로그, 비밀정보 `.env` 관리(v3 L1031·L959).

### Minor

- m1. RAG의 용도가 정의되지 않았고, "완성분 유지"(v3 L531)가 그린필드 방침(L1040)과 모순된다.
- m2. VRAM 근거가 문서끼리 다르다. STT는 R-llm L51이 int8, R-stt L21은 INT8 불가로 적었다. TTS는
  R-llm L52가 1~2GB, R-tts는 약 0으로 적었다.
- m3. v1에서 의미가 없는 정책이 정본 문서에 섞여 있다(v3 L717·L972·L979).
- m4. 월 $10~25 클라우드 비용(v3 L8)에 계산 근거가 없다. 오탐, 이력, 롤링 요약, 2회 왕복이 빠졌다.
- m5. 숫자·단위를 한글로 낭독하는 일을 LLM 프롬프트에 맡겼다(v3 L626). 템플릿 경로인
  `tts_announce`에는 적용되지 않으므로 TTS 앞단에 텍스트 정규화가 필요하다.
- m6. "저신뢰 되묻기"(v3 L971)에 쓸 confidence가 faster-whisper에서는 정의되지 않는다.
- m7. `control_device`의 value 타입에 제약이 없다. enum은 "동적 생성"이라면서 예시는 하드코딩이다
  (v3 L644-646).
- m8. LAN WSS 인증서와 Android 신뢰 구성이 정의되지 않았다. Caddy, Tailscale, JWT, OAuth가 겹친다.
- m9. 우선순위가 문서마다 다르다. Matter는 FS에서 P2, v3에서 P1이다. 끼어들기(barge-in)는 v3 L112에서
  P0, L891에서 옵션이다.
- m10. "플랫폼 AEC는 신뢰 불가가 실측 결론"(v3 L45)이라고 했지만 이 프로젝트가 측정한 적은 없다.

### 2026-11 기준 외부 변화로 낡은 결정

외부 조사 결과다. "확인"으로 표시한 항목은 이 검토에서 1차 출처를 직접 열어 확인했다. 나머지는
조사 결과를 옮긴 것이므로 해당 스파이크나 ADR에서 다시 확인한다.

## 조치와 잔여 위험

재설계는 v3를 고쳐 쓰지 않는다. 먼저 다음 기본 가설을 세우고 스파이크로 반증을 시도한다.

> 기기와 자동화는 Home Assistant에 맡긴다. 직접 만드는 것은 한국어 음성 경험, 앰비언트 허브 UI,
> 원격 앱이다. 상시 가동은 저전력 Linux 서버가 맡고, GPU 데스크톱은 필요할 때만 쓰는 추론 노드로 둔다.
> 알람처럼 실패가 허용되지 않는 기능은 허브가 로컬에서 소유한다.

이 가설의 목표 구조는 `docs/design/`의 시스템·서버·허브·휴대폰 앱 설계안에 있다. 스파이크는 아래
순서로 진행한다. 앞의 두 개가 허브 하드웨어와 음성 경로를 결정하므로 다른 결정보다 먼저다.

| 순서 | 스파이크 | 확인할 것 | 결정되는 것 |
|---|---|---|---|
| S1 | 태블릿 기종과 원거리 웨이크워드 | 후보 태블릿 1~2대, 화자 3명 이상, 1·3·5m 거리, 한국어 TV를 배경으로 24시간. microWakeWord / LiveKit wakeword / 커스텀 한국어 모델의 미탐률, 하루 오탐 수, CPU 사용률. 합격선은 시작 전에 정한다(예: 3m 미탐률 ≤10%, 오탐 ≤1회/일) | 태블릿 기종, 웨이크워드 엔진과 호출어 |
| S2 | 음성 경로 3안 비교 | (a) 로컬 STT + 클라우드 LLM + 로컬 TTS, (b) 클라우드 STT/LLM/TTS, (c) 툴 호출을 지원하는 실시간 음성 API. 한국어 명령 50개로 허브에서 잰 발화 종료 → 첫 소리 p50/p95, 툴 정확도, 1회당 비용 | 음성 파이프라인 구조와 서버의 GPU 필요 여부 |
| S3 | Home Assistant 반증 | HA + Tapo + Matter 기기 1종 + HA MCP 서버로 한국어 명령 20개를 처리하고 방(area) 인지 여부를 확인. 산출물은 HA로 안 되는 것의 목록 | 기기 레이어 위임 여부와 자체 서버의 책임 범위 |
| S4 | 서버 하드웨어 | 데스크톱의 24시간 전력·소음 실측, 저전력 미니PC와 비교. CPU로 STT를 돌릴 때의 지연 | 상시 서버 기종 |
| S5 | Android 72시간 상시 구동 | HOME 앱 기준, LockTask·Device Owner 유무별로 마이크 캡처 연속성, 재부팅·크래시·업데이트 후 복귀, 발열, Android 17 오디오 제한 준수 여부 | 키오스크 방식 |
| S6 | 에코와 self-wake | TTS·알람·미디어 재생 중 오탐 횟수, 알람이 울리는 중 음성 정지 가능 여부, WebRTC APM 적용 시 개선폭 | AEC 적용 범위, 끼어들기 지원 여부 |
| S7 | 알람 신뢰성 | 허브 AlarmManager 방식과 서버 push 방식을 서버 종료, 연결 단절, 허브 재부팅 상황에서 비교 | 알람 소유 위치 |
| S8 | 한국어 TTS 청취 비교 | Qwen3-TTS, Supertonic 3, 클라우드 2종으로 숫자·시간·단위가 들어간 문장 30개 블라인드 청취 | TTS 엔진 |
| S9 | 결정론 명령 커버리지 | 1주간 실제 발화 로그에서 템플릿 경로가 처리하는 비율 | LLM 폴백 범위 |

S10(Matter 직접 운영)은 S3에서 HA를 채택하지 않을 때만 진행한다.

### 남는 위험

- 외부 조사 결과 중 실시간 음성 API의 모델명·가격·한국어 품질, Qwen3 계열의 한국어 품질, SmartThings
  한국 제공 여부는 확인하지 않았다. 해당 스파이크와 ADR에서 1차 출처로 다시 확인하기 전에는 결정
  근거로 쓰지 않는다.
- Kiosk Satellite는 비상업·변경 금지 라이선스다. 참고 구현으로만 쓸 수 있고 코드를 가져올 수 없다.
- Home Assistant에 위임하면 HA 업데이트에 따른 호환성 변화(툴 이름 규칙 변경 등)를 계속 따라가야 한다.
  S3에서 이 결합 지점을 MCP와 HA WebSocket API 두 곳으로 제한할 수 있는지 확인한다.
- 이 검토는 원문과 외부 자료를 읽고 판단한 것이며 실측을 포함하지 않는다. 지연·정확도·전력에 관한
  모든 수치 판단은 스파이크 결과로 대체한다.
